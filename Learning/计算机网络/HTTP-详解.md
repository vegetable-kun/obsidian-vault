> [!tip] 学习目标

## 📖 第一章 入门（请求/响应格式与方法）

### 1.1 HTTP 请求与响应的结构

**知识点详解**

| 部分 | 说明 | 示例 |
|---|---|---|
| 请求行 | 方法 + URI + HTTP 版本 | `GET /index.html HTTP/1.1` |
| 请求头 | 元信息键值对 | `Host: example.com` |
| 空行 | 头与体的分隔 | `\r\n` |
| 请求体 | 可选，携带数据 | POST 表单、JSON |
| 响应行 | 版本 + 状态码 + 原因短语 | `HTTP/1.1 200 OK` |
| 响应头 | 元信息键值对 | `Content-Type: text/html` |
| 响应体 | 可选，返回内容 | HTML、JSON、二进制 |

> [!tip] 记忆技巧
> HTTP 是“文本驱动”的协议（至少在 1.1/2 初期可读性强），请求=“我要什么”，响应=“结果与元信息”。

**填空题（每章 4 道，答案见本节末尾）**

1. HTTP 请求的第一行由 ______、______、______ 三部分组成。
2. 请求头与请求体之间必须用 ______ 分隔。
3. 响应行格式为 ______、______、______。
4. 表示“成功处理请求”的状态码类别是 ______。

**答案**：
1. 方法, URI, 版本
2. 空行（\r\n）
3. 版本, 状态码, 原因短语
4. 2xx

### 1.2 HTTP 方法语义

**知识点详解**

| 方法 | 语义 | 安全/幂等性（常见） |
|---|---|---|
| GET | 获取资源 | 安全、幂等 |
| HEAD | 获取首部，不返回体 | 安全、幂等 |
| POST | 提交数据，触发处理 | 不一定安全/幂等 |
| PUT | 替换资源 | 幂等（通常） |
| DELETE | 删除资源 | 幂等（通常） |
| PATCH | 部分修改资源 | 不一定幂等 |
| OPTIONS | 查询服务器支持的方法/跨域 | 安全、幂等 |

> [!warning] 注意
> 方法的语义由规范定义，但服务器实现可能差异；“安全”指不改变服务器状态，“幂等”指多次执行效果相同。

**填空题**

1. 用于获取资源且通常不改变服务器状态的方法是 ______。
2. 仅获取响应首部而不返回响应体的方法是 ______。
3. 用于提交数据并触发服务器处理的方法是 ______。
4. 用于查询服务器支持哪些方法（常用于跨域预检）的方法是 ______。

**答案**：
1. GET
2. HEAD
3. POST
4. OPTIONS

### 1.3 状态码分类与常见码

**知识点详解**

| 类别 | 范围 | 含义 | 常见示例 |
|---|---|---|---|
| 1xx | 100-199 | 信息 | 100 Continue |
| 2xx | 200-299 | 成功 | 200 OK, 201 Created, 204 No Content |
| 3xx | 300-399 | 重定向 | 301 Moved Permanently, 302 Found, 304 Not Modified |
| 4xx | 400-499 | 客户端错误 | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 405 Method Not Allowed |
| 5xx | 500-599 | 服务器错误 | 500 Internal Server Error, 502 Bad Gateway, 503 Service Unavailable |

**填空题**

1. 表示“资源已永久移动”的重定向状态码是 ______。
2. 表示“未修改，可使用缓存副本”的状态码是 ______。
3. 表示“服务器暂时无法处理请求”的状态码是 ______。
4. 表示“请求方法不被支持”的状态码是 ______。

**答案**：
1. 301
2. 304
3. 503
4. 405

### 1.4 首部字段基础

**知识点详解**

| 首部 | 位置/用途 | 示例 |
|---|---|---|
| `Host` | 请求必需，指定目标主机与端口 | `Host: example.com` |
| `User-Agent` | 客户端信息 | `Mozilla/5.0...` |

| `Content-Length` | 请求/响应体字节长度 | `Content-Length: 1234` |
| `Connection` | 连接管理 | `Connection: keep-alive` |
| `Cookie` / `Set-Cookie` | 会话/身份信息 | `Cookie: session=abc` |

3. 用于管理会话/身份信息的首部对是 ______ 与 ______。
4. 表示连接复用的常见值是 ______。

**答案**：
1. Host
2. Content-Type
3. Cookie, Set-Cookie
4. keep-alive

> 1. **方法与语义混淆**：POST 不一定是“创建”，语义由服务器实现与上下文决定。

## 📖 第二章 进阶（缓存、持久连接与跨域）

### 2.1 HTTP 缓存：强制缓存与协商缓存

**知识点详解**

| 缓存类型 | 控制方式 | 行为 |
|---|---|---|
| 强制缓存 | `Cache-Control: max-age` / `Expires` | 在有效期内直接返回缓存，不与服务器通信 |
| 协商缓存 | `ETag` / `If-None-Match` 或 `Last-Modified` / `If-Modified-Since` | 缓存过期后与服务器比对，命中返回 304 |

> [!tip] 记忆技巧
> 强制缓存看“过期时间”——命中直接返回；协商缓存看“标识比对”——命中返回 304，否则返回 200 新内容。

**填空题**

1. `Cache-Control: max-age=3600` 表示资源在 ______ 内被视为新鲜。
2. 强制缓存命中时，服务器通常 ______（无需通信）。
3. 协商缓存使用 `ETag` 与客户端的 `If-None-Match` 配合，命中时返回 ______。
4. `Last-Modified` 与 `If-Modified-Since` 是基于 ______ 的协商缓存。

**答案**：
1. 3600 秒
2. 不需要（或不与服务器通信）
3. 304
4. 修改时间（时间戳）

#### 2.1.1 缓存指令的真实语义（最容易背错的部分）

| 指令 | 能否存储 | 能否直接复用 | 说明 |
|---|---|---|---|
| `max-age=N` | ✅ | ✅ N 秒内 | 基础新鲜期 |
| `no-cache` | ✅ **能存** | 🔴 必须先验证 | ==名字骗人：不是「不缓存」==，是「不信任」 |
| `no-store` | 🔴 **完全不存** | 🔴 | 任何缓存都不写，含浏览器 |
| `must-revalidate` | ✅ | 过期后必须验证 | 断网时返回 504，不给陈旧响应 |
| `immutable` | ✅ | ✅ 且免验证 | 配合长 `max-age` 用于带 hash 的静态资源 |
| `s-maxage` | 仅共享缓存 | ✅ | CDN 用的新鲜期，覆盖 `max-age` |
| `private` | 仅私有缓存 | — | 含用户数据的响应禁止进 CDN |
| `stale-while-revalidate` | ✅ | ✅ 先给旧的、后台更新 | 弱网体验优化 |

> [!danger] 最常见的两个误解
> ① `no-cache` ≠ 不缓存（它只是强制每次验证）；要「不缓存」得用 `no-store`。
> ② `max-age=0` + `must-revalidate` 是为了兼容老 HTTP/1.0 缓存的变通写法，==现代场景直接用 `no-cache` 即可==。

#### 2.1.2 ETag：强校验器、弱校验器与乐观锁

| 类型 | 形式 | 含义 | 可用于 Range |
|---|---|---|---|
| 强 ETag | `"6868976"` | ==逐字节相同== | ✅ |
| 弱 ETag | `W/"6868976"` | 语义等价，字节可能不同 | ❌ |

```bash
# 缓存验证（省带宽）
curl -I https://example.com/a.js
curl -I -H 'If-None-Match: "6868976"' https://example.com/a.js   # → 304

# 乐观并发控制（防丢失更新）
curl -X PUT -H 'If-Match: "6868976"' https://example.com/a.js     # 不匹配 → 412
```

> [!tip] 选型
> 静态资源 ==用内容 hash 做 URL + `max-age=31536000, immutable`==，彻底不验证；动态接口用强 ETag。
> ETag 若依赖 inode/时间戳，在多机负载均衡下会不一致 → 缓存命中率暴跌，==应基于内容生成==。

**填空题**

1. `no-cache` 允许 ______ 响应，但复用前必须先验证。
2. 完全禁止任何缓存存储应使用 `no-______`。
3. 弱 ETag 的前缀是 `W/`，表示内容 ==字节相同/语义等价==。
4. 用 `If-Match` 做乐观锁失败时服务器返回 ______。

**答案**：
1. 存储
2. store
3. 语义等价
4. 412 Precondition Failed

### 2.2 持久连接与连接管理

**知识点详解**

| 内容 | 说明 |
|---|---|
| 持久连接（keep-alive） | HTTP/1.1 默认复用 TCP 连接，减少握手开销 |
| 连接复用好处 | 减少握手时延、降低服务器压力 |
| 并行与串行 | HTTP/1.1 仍有队头阻塞（串行请求），多个连接可并行，但受限 |
| 超时与关闭 | 服务器/客户端可关闭空闲连接 |

**填空题**

1. HTTP/1.1 中，默认的连接复用模式是 ______。
2. 持久连接的主要好处是 ______。
3. HTTP/1.1 在单个连接上请求串行处理，可能导致 ______。
4. 空闲连接可能被 ______ 关闭。

**答案**：
1. keep-alive（持久连接）
2. 减少握手时延/连接开销
3. 队头阻塞（串行等待）
4. 服务器或客户端（或超时）

#### 2.2.1 消息体如何结束？`Content-Length` vs `Transfer-Encoding`

| 方式 | 首部 | 效果 |
|---|---|---|
| 定长 | `Content-Length: 1234` | 客户端读满 N 字节即结束 |
| 分块 | `Transfer-Encoding: chunked` | 服务端边生成边发送，==每块自带长度，最后 0 块收尾== |
| 关闭连接 | 无 | HTTP/1.0 常见；HTTP/1.1 除非明确，否则不能用关连接来定界 |

> [!warning] 安全坑
> 同时存在 `Content-Length` 与 `Transfer-Encoding` 时，历史上有 **Request Smuggling（请求走私）** 风险；反代（nginx）与后端解析不一致就会被利用。生产配置应只允许一种。

#### 2.2.2 Cookie 与会话安全（结合你的安全主线）

| 属性 | 作用 | 缺失后果 |
|---|---|---|
| `HttpOnly` | JS 读不到 | 缓解 XSS 窃取 Cookie |
| `Secure` | 只走 HTTPS | 明文 HTTP 下泄露 |
| `SameSite=Lax/Strict/None` | 限制跨站携带 | 缓解 CSRF（`Lax` 是现代浏览器默认） |
| `Max-Age/Expires` | 持久化时间 | 不设则是会话 Cookie |

> [!tip] 与安全笔记联动
> 会话劫持、CSRF 的完整攻防见 [[TLS-与证书安全]] 与 [[网络诊断与安全]]；本节只强调「HTTP 层的会话属性同样是安全边界」。

### 2.3 跨域基础（CORS）与 OPTIONS

**知识点详解**

| 内容 | 说明 |
|---|---|

1. 同源策略
2. OPTIONS（预检）
3. Access-Control-Allow-Origin（等）

> 1. **缓存混淆**：`max-age` 是相对时间，`Expires` 是绝对时间；协商缓存未命中返回 200，而非 304。

> 4. **DNS 缓存干扰**：本地/ISP/浏览器可能缓存记录，排查域名解析时需多级确认。

## 📖 第三章 高级（HTTP/2、HTTP/3 与性能差异）

### 3.1 HTTP/2：多路复用、HPACK 与队头阻塞局限

**知识点详解**

| 特性 | 说明 |
|---|---|
| 多路复用 | 单个连接上并行发送多个流（请求/响应），避免应用层队头阻塞 |
| 头部压缩 | HPACK 减少冗余头开销 |
| 二进制分帧 | 协议格式变为二进制帧，更高效解析 |
| 服务器推送 | 服务器可主动推送资源（使用已减少） |
| 队头阻塞局限 | HTTP/2 解决了应用层阻塞，但 TCP 层丢包仍会阻塞所有流 |

> [!warning] 注意
> HTTP/2 仍基于 TCP，TCP 层的丢包会阻塞所有复用流；这也是 HTTP/3 切换到 QUIC 的动机之一。

**填空题**

1. HTTP/2 的关键特性之一是 ______，允许多个请求/响应在一个连接上并行。
2. HTTP/2 使用 ______ 压缩重复的头部字段。
3. HTTP/2 的协议格式采用 ______ 帧，提升解析效率。
4. HTTP/2 无法解决 ______ 层丢包导致的队头阻塞。

**答案**：
1. 多路复用
2. HPACK
3. 二进制
4. TCP

### 3.2 HTTP/3 与 QUIC：基于 UDP 的演进

**知识点详解**

| 内容 | 说明 |
|---|---|
| QUIC 基础 | 基于 UDP 的传输协议，集成加密与多路复用 |
| 握手优化 | 减少往返，支持 0-RTT/1-RTT 连接建立（视情况） |
| 独立流 | 每个流独立处理，避免 TCP 层丢包阻塞所有流 |
| 连接迁移 | 基于连接 ID，可在网络变化时保持连接 |
| 适用场景 | 不稳定网络、移动网络、高延迟环境优势更明显 |

**填空题**

1. HTTP/3 使用 ______ 作为传输层基础。
2. QUIC 的一个关键优势是各流 ______，避免 TCP 层丢包阻塞所有流。
3. 相比「HTTP/2 + TCP + TLS」，HTTP/3 的 QUIC 握手往返次数更 ______。
4. QUIC 支持 ______ 功能，可在网络变化时保持连接。

**答案**：
1. QUIC（运行在 UDP 上）
2. 独立（独立处理）
3. 少（0-RTT/1-RTT）
4. 连接迁移（或基于连接 ID）

### 3.3 HTTP 性能对比与抓包观察

**知识点详解**

| 对比维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 连接模型 | 串行/多个连接 | 单连接多路复用 | 单连接多路复用（QUIC） |
| 队头阻塞 | 应用层+连接数限制 | 应用层解决，TCP 层仍有 | 传输层独立，改善 |
| 头部编码 | 文本头 | HPACK 压缩 | 继承优化 |
| 握手 | TCP + TLS（多次往返） | TCP + TLS | QUIC 握手优化 |
| 丢包表现 | 发送受限 | TCP 丢包阻塞所有流 | 流独立，影响较小 |

> [!tip] 关键理解
> HTTP/2 解决了应用层队头阻塞，但 TCP 层丢包仍会阻塞所有流；HTTP/3 将传输层独立化，改善了丢包环境下的表现，但部署与中间设备兼容仍需考虑。

**填空题**

1. HTTP/1.1 在单个连接上请求 ______ 处理，可能导致阻塞。
2. HTTP/2 在应用层解决了队头阻塞，但 ______ 层丢包仍会阻塞所有流。
3. HTTP/3 将传输层基于 ______ 构建，各流 ______ 处理。
4. QUIC 支持的 ______ 功能允许网络变化时保持连接。

**答案**：
1. 串行
2. TCP
3. QUIC, 独立
4. 连接迁移（或连接 ID）

**填空题（本章共 4 道，答案见下方）**

> [!tip] 常见陷阱
> 1. **HTTP/2 ≠ 总是更快**：在丢包严重的 TCP 环境中，HTTP/2 可能因 TCP 队头阻塞而受限。
> 2. **HTTP/3 误认为“完全取代”**：HTTP/3 在部分场景优势明显，但部署、兼容与中间设备支持仍是现实考量。
> 3. **服务器推送过度使用**：服务器推送可能造成资源浪费，现代实践多减少或取消。
> 4. **HPACK 误解**：HPACK 是头压缩，不是内容压缩；内容仍由 `Content-Encoding` 控制。

## ❓ 常见问题

> [!faq]- Q：`no-cache` 到底能不能缓存？
> A：**能存**。它的意思是「每次复用前必须回源验证」。要「不落盘、不存储」用 `no-store`。

> [!faq]- Q：为什么我的接口每次都返回 200 而不是 304？
> A：常见原因 ① 响应没有 `ETag` / `Last-Modified`；② ETag 基于 inode/时间戳，多机部署不一致；③ 中间层（CDN/nginx）清掉了首部；④ 响应带 `no-store` 或 `Vary` 过多。

> [!faq]- Q：HTTP/2 一定比 HTTP/1.1 快吗？
> A：不一定。HTTP/2 仍跑在 TCP 上，==一次丢包会阻塞该连接上的所有流==。高丢包/高 RTT 环境下，HTTP/3（QUIC）才真正解决队头阻塞。

> [!faq]- Q：`Transfer-Encoding: chunked` 为什么必须知道？
> A：说明响应长度未知、边生成边发。抓包里看到大量 chunk，且首部同时出现 `Content-Length`，要警惕 ==Request Smuggling==（nginx 与后端解析不一致）。

> [!faq]- Q：Cookie 没设 `SameSite` 有什么风险？
> A：浏览器默认已是 `Lax`（现代浏览器），但老浏览器会带 Cookie 访问跨站 GET → CSRF 风险。涉及状态的接口应显式设 `SameSite` 并配合 CSRF Token。
